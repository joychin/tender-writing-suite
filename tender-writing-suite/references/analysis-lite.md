# 要点提取（简版）——目录与正文所需的四张登记表

本技能只需要四类机器可消费的清单 + 废标全扫，判定依据以本文件为准。
执行前先读 `@references/evidence-rules.md`（证据边界、出处引用键、检索纪律、防注入）。

产物落 `work/analysis/`，每件一个 .md，**行序=编号、定稿后不插行/删行/换序**
（目录与合册按编号对账，行序漂移=全部引用悬空）：

## 1. structure.md（结构事实——只取目录需要的字段）

| 字段 | 说明 |
|---|---|
| 项目名称 / 项目编号 / 采购人 | 骨架的 `## 项目信息` 段用 |
| 截止时间类 | **必须区分**递交截止/澄清截止/开标时间，没有原文等同性不能互相补全 |
| 包/标段划分 | 分标段投标时通常每标段一套响应文件 |

每行带出处引用键（`文件名 章节名（L行号区间）`）；末尾 coverage 声明（已检查：…；未检查：…）。

## 2. requirements-format.md（格式要求——目录骨架输入）

三节严格照抄结构：

```
## 一、投标文件结构要求
<概括描述 + 结构大纲（无编号列表，缩进表达层级；**不用 ``` 代码围栏包裹**）>

## 二、必须有的章节（mandatory chapters）
| 序号 | 章节名称 | 归属(bidPart) | 原文出处线索 |
（归属：qualification/commercial/technical/pricing/unknown）

## 三、招标方给出的章节示例 / 模板（templates）
| 序号 | 模板名称 | 归属(bidPart) | 对应必须章节 | 原文出处线索 |
```

- mandatory_chapter = 原文明确「必须提供/须包含」的章节；template = 招标方给出的
  格式模板/表格样张（投标函、授权委托书、偏离表、报价一览表等）。
- 「投标文件由以下部分组成…」写进「一、」的结构大纲——它决定响应文件划分。
- 结构大纲直接写缩进的 `- ` 列表（2 空格一层）——包进代码围栏时围栏行会作为散文
  泄漏到分析报告上（解析器按行分类，不识别 ```）。
- 出处线索须带行号区间，每行带文件名或「同文件」标记。

## 3. requirements-business.md（商务技术要求——REQ 登记表）

```
## 商务技术要求清单
| 需求（原文 verbatim 片段） | 出处（章/节/附件编号） |
```

- 一条 = 一个可独立响应的功能要求，**禁止把整个模块压成一条**（mega 行让偏离表
  无法逐条响应）；压缩不丢限定（括号内限定语/例外条件保留）；入表后回区段逐行
  反查无遗漏；原文模糊表述照抄并登记待澄清（不改写语义）。
- 背景不进表，但夹带的硬约束要捞——判别法：这句话若影响投标方案、架构或报价，
  就不是纯背景（部署地点/接入方式/数据驻留/计价方式常藏在背景段）。

## 4. evaluation.md（评分标准——SCORE 登记表）

```
## 评分标准清单
| 评分项 | 分值 | 评分要点 | 出处 |
```

- 用 outline 定位评标办法章节 + 逐词检索（评分/评标/得分/分值）。
- 评标表格跨页/合并单元格/抽取失真——逐行核对，拼不上宁可弃掉并登记澄清，不编数值；
  PDF 来源的评分表/前附表，框线与合并格**以解析页图目视核对为准**（pages/ 页图），
  扫描件转写档的数值须页图复核后才入表。
- 资格门槛不是评分项，除非原文明确计入总分；分值类型如实标注（数值/区间/公式/
  定性/通过制/加减/未知）。

## 5. disqualification.md（废标条款——唯一强制全扫）

**覆盖所有来源文件全文逐章扫描** + 20 词反查（逐词各检索一次、同批并行发出，
豁免次数预算与停止规则；自扩词同样逐词）：

`无效、否决、拒收、不予受理、不合格、取消、废标、作废、放弃、撤回、拒绝、不予接受、不被接收、失效、罚金、违约金、没收、无权参加、列入、实质性响应`

**输出形态（评审台废标区按此解析，勿改列名）**：条目写成一张表格，表头固定四列
`| 条款摘要 | 触发条件 | 后果 | 出处 |`，每条一行——评审台按行渲染全量条目。

词表是下限不是上限：遇到新的「后果=出局/受罚」表述立即用原词对全部来源反查。
宁滥勿缺——误召回只多读几行筛掉，漏召回是整标被废。判定边界：项目终止不是
投标人废标；普通「应」字不自动成为废标条款；每条写清触发条件与后果。
扫描件转写档来源的废标条款，条款文字与数值**页图复核后**才入表（转写文本
不直接当判据）。
coverage 声明逐词列出实际使用的词（含自扩词）；覆盖不足时明确写
「检查范围不完整，本清单不能视为全部废标项」。

## 澄清与收尾

- 影响目录/正文的冲突、缺失、不足 → 登记 `work/analysis/clarifications.md`
  （CLAR-xx 编号、类型冲突/缺失/歧义、问题、影响范围、建议动作）；普通未检索到
  不登记。**建议动作必填**（「向招标人/代理机构确认 X」式，不得留空）；解析警示
  与需留意问题在 G1 就亮给用户（不等本清单），见 @references/stage-gates.md。
  **第一步解析阶段已登记的初步澄清项沿用既有编号续排，不重开清单**。
- **重跑保护与校验钩子**：重跑覆盖任一登记表前先向用户声明（表内处理记录与
  用户手改会丢失），用户明示才继续；登记表收尾必跑 `check_writing.py --analysis`
  （coverage 声明与出处引用三层），全绿才算完工。
- **中立纪律（商业评述禁区）**：澄清条目只写事实层——口径冲突是什么、依据哪条
  原文、影响哪个取值/承诺/章节、建议向谁确认什么。禁止商业评价与经营测算：不写
  「陷阱/吃亏/划算/风险全在你」式利弊判断，不替用户测算人天/产能/工期/成本，不
  建议报不报价、投不投。商业账由用户与商务团队算，这里只把口径问题摆清。
- **处理记录**：用户答复澄清后在本文件末尾追加/更新 `## 处理记录` 段（助手经
  apply_review.py 写入，行式 `- CLAR-01 :: 处理=按建议 | 备注=… | 时间=…`；
  旧 `## 裁决记录`/`裁决=` 行仍可读，写入一律用新段名新键）；登记表行序不动
  （行序=编号），处理只进该段。
- 收尾向用户摆关键要点（废标最严几条、评分框架、资格硬门槛、递交形式），过 G2
  门停轮呈现；**六张登记表全量上分析报告**（项目基本情况/结构要求/商务技术要求/
  评分/废标/澄清，含各表覆盖范围声明；评审台不重复渲染，总览提供报告入口互链），
  对话不重复
  清单；澄清条目只读展示——用户要澄清哪条自己在对话里说；未处理项按
  @references/stage-gates.md 门规默认先行（批注标注）。

## 投标主体与家底确认（问答涉公司家底时）

问法涉及本公司家底（能得多少分/我们家缺哪些资质业绩/能不能投）时，先确认投标
主体与现有家底再回答：环境有知识库/资料库类检索工具就自查；没有就一轮问全——
投标人全称（联合体加问牵头方与分工）、资质证书与类似业绩清单（请用户传公司简介
或证书件）。确认结果（查得或问得）落 `work/body/关键事实与承诺.md`，后续进全流程
时直接沿用、不重复问；答案只按已确认的家底算，没有的资质如实标缺，不替用户
假设有。
