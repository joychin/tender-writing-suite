# 三道清理（固定顺序 ①→②→③）

对 `tender-response-docs.md` 每个响应文件的 `## 目录` 依次做三道修订。
跳过某道时向用户声明原因（如「已跳过评分对齐：无评分条目」）。
每道造成的新增/删除/改名节点，**同步更新** `## 来源标注` 与 `## 目录说明`
（新增节点立即补标注，无来源的过渡章不写标注行；删除节点移除标注行）。

## ① 查漏补缺（输入：目录 + requirements-business 的 REQ 清单；无 REQ 条目则跳过）

三条判定原则：

- **覆盖而非独占**：一条 REQ 已被某章节的 scope 覆盖即算满足，不为单条需求开新章；
- **横切需求**：同一条要求要在所有相关章节分别体现（如「数据安全」在架构/实施/
  运维章各自落实），不是集中一处；
- **实质主题成章**：多条需求共同指向同一主题、且该主题无章节承载时，才补一个
  专属章节。

同时排除程序性条款（封装/递交/废标/签章/联合体/保证金不进目录）。
**只补缺、不瞎加**——目录节点宁少勿滥。

## ② 评分对齐（输入：目录 + evaluation 的 SCORE 清单；无 SCORE 条目则跳过）

三个修订动作：

- **查漏补缺**：每个有分值的评分维度都有章节承接（无承接 = 这块分白丢）；
- **覆盖要点**：评分要点里的关键词（如「应急响应时间」「驻场人员」）应能在对应
  章节的 scope/概述中看出落点；
- **核心项置顶**：分值高的核心评分维度对应的章节，在不破坏逻辑流的前提下尽量
  前置（评委阅读疲劳是真实的）。

禁止：为凑评分造空章节；改动与评分无关的章节顺序。

## ③ 走查定稿（输入：目录 + 全部来源；无跳过条件）

五个动作 + 一次抽查：

- **删重复**：同一实质内容只留一个节点（跨册的边界写在 scope）；
- **合并近似**：「系统安全方案」与「安全保障措施」这类近似章合并成一个；
- **删装订属性条目**：命中下列词表的条目属独立递交材料，删除前**回原文核实**
  （先读该来源 outline.json 定位出处行号）：`无需装订、现场携带、无需上交、
  电子版单独提交、谈判现场使用、自行打印`；
- **兄弟章节逻辑流排序**：先写铺垫与被依赖的内容（需求理解→总体设计→分项设计），
  再写依赖它的核心内容，最后写收尾内容（服务承诺/培训/售后）；
- **同主体连续排布**：同一主体的内容（如全部涉密管理条款）连续排列，不穿插跳跃；
- **抽查核实**：从目录来源标注里抽不少于 3 条（不足 3 条全查），回原文核对出处
  行号与内容对得上——发现编造出处立即全面复查该册。

## 完成后

目录三段（目录/来源标注/目录说明）处于一致状态；向用户汇报目录概要
（各册章节数、三道清理各做了什么、跳过了哪道及原因）——停轮呈现；用户未明确
确认即按暂定稿进正文阶段（改动经下方增量走查回流）。

## 增量走查（用户在评审台改过目录之后）

用户改动（评审台保存/手工编辑 md）落盘后，**不整树重跑三道清理**，按 apply 报告的
旗标做增量：只对变更子树（新增/移动/改名节点及其兄弟）重跑 ①② 的覆盖判定与
对齐检查，③ 的删重排走查只在报告旗标命中（重名叶子/孤儿行）时做。新增节点补
来源标注与目录说明（无来源过渡章按纪律留空并旗标）；被删节点的写作指引行、
已建节文件由助手列出清单点名后随增量走查清理。增量完成后重新呈现目录概要
（未答复即视为接受，不追问）。
