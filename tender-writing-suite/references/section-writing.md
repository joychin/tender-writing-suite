# 逐节写作细则（素材先行）

每节一个 .docx，写作与修订全部经 `scripts/docx_toolkit.py`，模型不直接写 docx
二进制。三种模式的通用前置：动笔前把该节的「依据编号」回 analysis 对应表查出
要求原文与出处，需要格式原件区段的按出处行号定位。

**开工前重读三份文件**：目录树（outline/tender-response-docs.md）、写作指引、
关键事实与承诺——用户可能在评审台改过并已直接落盘（评审台保存直写这些文件），
以文件现状为准，不凭会话里的旧读数写作；指引行与目录树对不上时以目录树为准
并按 outline-cleanup 增量走查处理。

## 素材修订（默认模式）

1. **选材**：指引素材列已给「素材文件 + 行号区间」时直接采用；素材列标【缺】
   时按该节主题检索可用素材——**检索通道按当前环境实际具备的能力取用**：
   环境里有知识库/资料库/文档检索类工具（如平台内置资料库、ima、MCP 检索等，
   以真实存在的工具为准）就优先用它们；没有则向用户索取素材文件，用
   outline/关键词在文件里定位。命中素材后按通道能力分三级处理：
   - **本地文件**（用户上传）：记「文件名+行号区间」回填使用计划（保真拷贝
     依赖行号区间）；
   - **云端命中且环境具备导出/下载能力**（资料库导出、在线文档转 docx、
     网盘下载类）：**先落地为本地 docx 再走保真拷贝**——落地点固定
     `work/素材/`，文件名保留 .docx 后缀、以原素材名命名；与工作目录内已有
     素材文件重名时加「资料库-」前缀（解析产物目录按文件名生成，同名不同物
     会互串）。落地后与本地素材完全同权：parse_document.py 解析（幂等）→
     记「文件名+行号区间」→ copy-from 保真拷贝，指引素材列按落地文件名记；
   - **命中但取不到文件原件**（多数第三方知识库检索工具只有检索+读文本）：
     按文本参考撰写、批注注明素材来源，并**向用户点名**：「知识库命中了
     《X》，但该通道取不到文件原件，本轮按文本参考撰写；如需保真复用
     （图片/原表格样式），请导出 docx 后发我」。
   什么素材都没有 → 按推理撰写写、批注说明素材缺口。**认为指派素材与本节明显不符**（讲的行业/产品与本节主题无关）
   时：仍按计划使用并改写，同时用批注留一条以「素材异议」开头的说明（不符点、
   本节如何处理）——素材选择归用户拍板，你负责把问题带回去；
2. **列使用计划**：动笔前列「本节用哪些区间、各用在哪个部分」——把选材从
   「看过」变成「承诺」；同一素材区间不得进两节（节间查重兜底）；
3. **贴底稿（元素级保真）**：先 `create` 建节，再用 `copy-from` 把素材区段拷进
   节文件（段落/表格/图片原样保真；**素材原件必须是 docx 且已用
   parse_document.py 解析过**——拷贝按解析行号区间定位元素；非 docx 素材按
   文本参考自行撰写）。**docx 素材禁止跳过拷贝直接凭文本自写**：图片与原表格
   样式只有拷贝能进正文；EMF/WMF 图拷不进（工具逐张跳过并告警），该位置留空，
   需图处用 `render-page` 转 PNG 后 `image` 插入。素材区间以源文件的章/节标题
   开头时，拷入后用 `revise` 删掉该标题行——节文件里的一级标题只有本节标题
   一个，多出的源章标题会原样进合册交付稿成双章标题；
4. **改写适配**：`read` 读节视图拿段落序号 → `revise` 定向修订（旧项目名/
   公司名/参数按本次承诺清单改，围绕本项目要求调整结构）。保住素材的结构与
   事实，替换项目相关信息。读视图里标〔图×N〕的段是图片段，只改其前后文字，
   不要对图片段本身做删除；
5. **自查**：`check_writing.py --section <节路径>` 查素材使用率（重叠率过低=
   未实质使用）与残留提示。

教训：不按此流程、凭自身知识自由发挥时，素材不会被真正使用——质量显著下降。
**素材在场 ≠ 素材被用。**

## 格式跟随

按招标文件规定的格式/表格逐项响应：依据节点来源编号 → analysis 对应表行 →
出处行号 → 不自由发挥结构。

- **出处原件是 docx → 拷原件优先**：`create` 建节 → `copy-from`（源=招标文件
  解析产物，区间=出处行号；独立格式附件给整文件区间）把招标格式原样拷进节
  文件——格式逐字节保真，表格/函件不会重排走样 → `read` 拿段落序号与表格格
  坐标（T 序号 + R行C列）→ `revise` 填空适配（表格空格子 fill、旧值 replace；
  招标方信息保留、我方信息按承诺清单填，未定值用批注记待办）；
- pdf 原件无可拷元素 → 内容一次成形于 `create` 的 paragraphs（换行分段），
  微调走 revise；
- **公司事实填空优先级**（资质证书/注册信息/体系认证/注册资本/员工数等
  「我们是谁、有什么」的格子）：① 指引缺口列的【资料】命中事实——证书数字
  （注册号/有效期/覆盖范围）**照抄原文不改写**；② 指引里没有的，回环境
  知识库/资料库按字段名补查一次（证书号、有效期、注册资本这类字段名即
  检索词；**一格一查、不命中即止**，不反复换词）——命中即回填指引缺口列；
  **证书/资质类字段以用户提供的原件核实优先，库文本命中只作定位线索、
  不作终值**；③ 库里也没有的，现场读用户提供的资料文件核实后填；
  ④ 查不到才批注待办——**禁止凭印象编**（格式件空格漏填公司资质类内容，
  交付稿里就是空格子）。

## 临时参考件（用户说「参考/照着写」的非招标文件）

定位 = 写法参考；写作依据仍然是节点出处（MAND/REQ/SCORE），承诺数字仍只出自
承诺清单——案例两者都不是。

- **读法**：用 parse_document.py 解析（幂等）→ 先读 outline.json 按行号取相关
  区段，禁止整读全文（案例动辄几十页，整读烧上下文也读不细）；
- **只借写法不抄事实**：章节组织、论证顺序、表格设计、语言风格可借鉴；案例里的
  项目名/客户名/公司信息/数字/日期一律不进正文——残留扫描对这类文件**没有
  防线**，纪律是唯一防线；
- 与招标要求冲突时以招标文件为准（案例不是依据）；
- 案例叙述性内容进正文的唯一形态是**改写**，不整段拷贝；确有值得原样搬的表格
  样式/版式结构时，先向用户说明再动；
- 用了案例哪些写法，在完成汇报里说明一句。

## 物理附件（复印件类）

资质证书复印件、营业执照副本、票据凭证、信用查询截屏等物理附件位（目录形态
=模板或附件填充）——**每个附件位在整本里都必须有落点**：

- **指引缺口列有【资料】命中（含图）→ 贴图产出节文件**：`create` 建节 →
  `image` 逐张贴证书图（图源=用户提供的图片文件；原件是 PDF 扫描件时先用
  `render-page` 把对应页转成 PNG 再贴）——文字陈述证书、图片贴在陈述段之后；
  库里没有的证书不硬凑，批注点名待线下补；
- **全无命中 → 建壳节**：`create` 建节——标题 + 一行贴入位「（此处贴入：XXX
  复印件，加盖公章）」（与招标件自印「在此粘贴身份证复印件」同一惯例：材料
  贴上去即覆盖，不存在忘删占位文字的问题），再批注点名缺什么材料、需要谁提供；
  收尾汇报仍逐条点名。**废标级资格件（营业执照这类缺了直接否决的）绝不许只
  登记不建节。**

## 封面

树首「封面」节点的成形（合册时它是整本第一页、独占一页、不带页眉页脚）：

- **招标有封面格式样例且原件 docx** → 走格式跟随的拷原件路径：拷样例 →
  revise 填投标人名称/日期等空位；
- **无样例或样例是 pdf** → 排版成形：`create --title 封面` 建节（标题段合册时
  自动剥掉），body 块逐行插封面行，**大字行（项目名/册名）用 style 字段
  `cover-title`，落款行（投标人：xxx / 日期）用 `cover-sub`**，两块之间用空
  文本行（text 用全角空格「　」）撑开下沉定位；
- 字段值纪律：项目名/册名从目录取；投标人名称等只从承诺清单取（缺→批注待办，
  不编造）；日期只写用户消息里给出的今天日期（天级精度），**禁止自编日期**。

## 推理撰写

针对本项目写方案（技术路线、实施步骤、保障措施）：

- 全文一次成形于 `create` 的 **body 块序列（段落+表格混排）**——不逐段拼长文，
  局部补充才用 revise；纯文字节仍可用纯段落序列；段落块可带 `style`：
  `h2`/`h3`/`h4`（真标题样式，进导航大纲、合册按树深度接续节号；**`h1` 禁用**
  ——节标题走 `--title`，body 内再出 H1 就是双章标题）——写手只管结构层级，
  一个编号都不写；
- **表格类内容（人员配置/里程碑/进度计划/对比清单）用 table 块，不用流水句铺**
  ——评委按表找要点比按段落找快，流水句里的「（一）项目经理，1 名，签订在
  合同中。职责是…」就是该成表没成表的形态。写法示例：

  ```json
  [
    {"type": "p", "text": "我方组建专职实施团队，按招标文件第五章岗位口径配置，如下表："},
    {"type": "table", "caption": "项目团队岗位配置",
     "header": ["岗位", "人数", "职责", "是否签入合同"],
     "rows": [["项目经理", "1", "对本项目交付负总责，全程现场参与并主导实施", "是"],
              ["架构师", "1", "主持总体技术架构与集成方案设计", "是"]]},
    {"type": "p", "text": "同一成员可按招标口径兼任多个角色，兼任不降低履行质量。"}
  ]
  ```

  （表题自动落表格上方居中，表头自动加粗浅灰、跨页自动重复表头、数据行不跨页
  拆分；工期/人数等承诺值落表格格，不落图片，校验可读回做承诺对账。）

  **合并格与列宽**（自建表需要跨列/竖向合并时）——cell 写对象形态：

  ```json
  {"type": "table", "caption": "项目团队一览表",
   "header": ["姓名", "岗位", "证书", "编号", "驻场"],
   "rows": [["张明远", "项目经理", "PMP", "2803647", "是"],
            ["李思涵", "技术负责人", {"t": "驻场组合并示样", "vm": "restart"}, "", "是"],
            ["王一舟", "安全工程师", {"t": "", "vm": "continue"}, "", "是"]],
   "widths": [2, 2, 3, 3, 1]}
  ```

  `span`（跨 N 列）、`vm`（restart 起始 / continue 续行）可组合；每行各 cell 的
  span 总和必须等于表头列数——不齐会整表报错不产出，改好再建。`widths` 不写时
  按各列内容长度自动分配列宽（长内容列自动变宽）；列 ≥9 自动小
  字号紧凑边距；**宽表节（如 12 列资信/团队表）建节加 `--landscape` 出横版页**，
  合册自动做横版区段且页码连续。**招标格式件里的原表不走本引擎**——用 copy-from
  保真拷贝（合并格/样张逐字节保真），本引擎只服务自建表。
- **图示按指引图示列的计划产出**：分层/甘特类图示**优先 `diagram` 出真图 PNG**
  再用 `image` 插入（spec 格式见脚本 --help；环境无 matplotlib 或无中文字体时
  回落表格表达：层级列+职责列、任务×周次、里程碑行 ◆，并在批注或收尾说明）；
  纯叙述内容不配图（加图不加分），承诺函/函件类格式节禁配；多图插同一段之后
  时按**倒序发指令**（后插的落在前面，倒序发正序成）；图题注用 `image --caption`
  （自动居中 9pt 题注段），不手写题注块再后处理；走 `--caption` 时 spec 的
  `title` 留空（图内已画标题再配同名题注会页面上出现两次）；
- 承诺类数字（工期/人员/服务/报价口径）只引「关键事实与承诺」清单值；
- 企业事实优先用指引缺口列的【资料】命中事实（数字照抄）；拟投入承诺不是现状
  事实，数字一律重核。

## 通用纪律

- 缺料不阻塞：批注（锚定相关段落）继续写；待澄清/待核验同样落批注；
  **正文禁止【待补】【待澄清】占位文字**（会随交付稿打印出去）；批注收尾必须
  逐条点名；
- **标题不带数字编号**：建节 title 用目录里的原文名（合册按裸名对账，带编号会
  双标题）；节内小标题同样不写「一、」「1.1」式编号——章节编号由合册按目录树
  序自动加，模型自编编号必错（不知道树位置），层级用 Heading 2/3 样式表达
  （--section 与全局校验都会拦自带编号的小标题：「一、」「（一）」「1.」开头都算）；
- **节内小标题逐级递进**：从二级（Heading 2）起、不跳级不倒挂（二级下面才能
  出三级）；合册会把节内小标题摘出导航大纲、**按树深度降级并程序接续节号**
  （深度 2 节下 H2→H3 并编号 5.1.1 式；扁平目录=节直接挂册下时编 10.1 式
  ——编号归合册，写手一个号都不写）；
- 正文不带模型写的头部/元信息（干净文本，评委要看的是干净文本）；
- REQ/MAND/SCORE/TPL-xx 是内部对账编号，一个都不写进正文（无论从指引、目录
  还是对话里看到）；呼应招标要求用要求内容本身或招标文件真实印着的章节/条款号
  （如「按第三章 2.3 条」——评标人能对照原文，内部编号他们对不上）；
- 写一节前浏览同层已写节的开头段，避免跨节重复表达；
- 一节写完即 `check_writing.py --section` 自查，不留到最后；
- 模型不直接改 docx 二进制：内容修改一律走 revise（含表格 fill），修不动时
  删除该段重建，不要手工编辑文件。

## 语言纪律（生成文字去 AI 腔）

**作用域**：只管你自己写出的文字——推理撰写的全文、素材修订里新增/改写的
段落、格式跟随里自写的说明文字。素材底稿与拷贝的招标格式件**原样保留一个字
不润**：为去腔重写素材会被判「未实质使用」、破坏保真；动招标方的格式件是事故。

七条规则：

1. **砍不携带信息的开场**：「为了实现这一目标，我们将…」删前半句；「值得注意的是，
   系统支持…」删「值得注意的是」——句子里没有信息量的引子一律去掉；
2. **不堆夸大修辞**：「标志着」「至关重要」「彰显了」「奠定坚实基础」「保驾护航」
   这类词评标人一眼扫过、不留任何信息——评审看的是逐条响应了什么要求。把抒情句
   换成实际措施：不写「为后续运维奠定坚实基础」，写运维频次、响应时限、备件方式；
3. **归因必须可溯**：「行业专家认为」「大量实践证明」「业界普遍认同」这类给不出
   出处的归因整句删——要引用就引招标文件原文或用户资料里可查证的事实；
4. **排比有几分写几分**：为凑数硬编的三点、硬造的对仗（「高效、可靠、安全」式
   三连）改成按实际内容组织——措施是两条就写两条；
5. **句子到事实为止**：「……，确保了项目顺利开展」「……，为后续工作提供了有力
   支撑」这类尾缀评价删掉，陈述完事实就收句；
6. **不用口号收尾**：「我们有信心、有能力、有决心圆满完成…」整句删，用具体
   措施与承诺清单值收尾；
7. **少用「不是A而是B」式拔高**：「这不仅是一次系统部署，更是管理理念的升级」
   → 直接写部署了什么、解决了什么。

标书允许规整句式（评审按点扫描，结构清晰是优点）——要避免的是每段同长同构
叠加空洞修辞，不是句式本身。
