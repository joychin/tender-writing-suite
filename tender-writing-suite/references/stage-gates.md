# 阶段确认门（stage-gates——分析阶段报告+对话，G3 起评审台是唯一确认面）

纪律总则：确认面分两段——**分析阶段确认面=只读分析报告+对话**（G2 全量交付；
G1 是异常门——解析警示/来源未决才停轮，正常路径并入 G2）（澄清等
全部内容直接呈现在报告里，用户要澄清/纠正哪条在对话里说）；**G3-G6 评审台是唯一
确认面**——每道门刷新页面并锚到对应区（命令与通道矩阵见
@tender-review/references/review-workbench.md），逐条内容（缺口/承诺值/废标与评分明细）只在
页面呈现。对话停轮只发**指针**：一行结论 + 待办去向一句话 + **「需要你补充」表格**
（有未决项时必给：`| 需补充 | 影响 | 不补充的处理 |`，「不补充的处理」一律写
「Word 批注标注，可后补」）+ 固定告知**「不补充也可以继续往下——缺失部分会以
Word 批注标在正文对应位置」** + 至多 3 条标题级提醒，不重复清单。表内逐项
点名澄清清单的未决项；指针放不下时至少写一句「另有 N 项已在分析报告登记，
不补充按批注处理」——不许只列三类就当作全量。答复处理：

- **明确确认 / 明确指引** → 照办，推进下一步；
- **答复但不明确**（「继续」「先这样」「你看着办」）或**只答部分** → **不追问、
  不阻塞**：未确认部分按本门声明的默认方案先行，并以注释标注待确认项。「先行」
  的边界=推进到**下一门的产物落盘为止**——下一门交付确认面后照常停轮收指针；
  「继续」不是跨门连跑授权，门与门不得同轮连过（写节前置自检见下方专条）。
  **判定「当门」**：用户这句「继续」越过的是**上一轮停轮的那道门**，只推进到
  紧随其后的那道门产物落盘为止。例：G2 交付后停轮 → 用户回「继续」→ 只做
  G3 目录树 + 评审台 → 交付 G3 后停轮；本轮**不得预做或宣布「现在生成
  G4/G5 指引与承诺」**（那是下一门产物，只能等用户对 G3 的答复后再做）。
  另：拆分/装订多方案这类「需要用户给值的岔口」不受「继续」影响，仍须停轮
  提问——「继续」是对上一道门的答复，不是对岔口问题的选择（见
  @tender-analysis/references/response-files.md 确认点操作）。
- **纠正 / 补充** → 按用户意见办；
- 用户对澄清/目录/承诺的处理答复与拍板 = 等效确认（写台账 work/decisions.json）；
  门的 pass 状态由 agent 依对话答复写入台账，页面不展示门进度（待办卡即用户视角的
  全部）。

同一问题只问一次，不反复追问。指针与停轮的硬边界：**报告/评审台交付或刷新后，
当轮以指针收束——指针之后不得再发起推进动作**（连续模式已获用户明确授权除外）；
页面 URL 一律按 Markdown 链接发出（裸代码串不算交付，宿主按链接渲染可点击入口）。

## 六道门

| 门 | 时机 | 页面锚点 | 页面呈现 | 对话指针 | 未明确时的默认方案 |
|---|---|---|---|---|---|
| G1 解析确认（异常门） | 第一步，仅异常时停轮 | 只读分析报告（`--pages report`，不产评审台） | 概况表 + 解析警示（扫描件须呈现「视觉转写档、关键值须页图复核」）+ 已登记的初步澄清项 | 解析概况一段（主文件/规模/可信度）+ 警示逐条 + 「要纠正直接回复」 | **无警示且来源角色已决 → 不停轮不产报告，直接要点提取**（解析概况并入 G2 交付）；有警示或来源未决才停本门，按声明假设推进、纠正后重解析 |
| G2 要点与澄清 | 第二步收尾 | 只读分析报告（正常路径首次全量交付） | 六张分析表全量呈现（项目基本情况/投标文件结构要求/商务技术要求/评分/废标/澄清清单，逐条带问题/影响/建议动作；第一节概况表含解析结论） | 解析概况一句（主文件/规模/识别方式——正常路径解析结论在此首次面世）+ 废标最严几条、评分框架、资格门槛的结论级摘要——只述事实与出处，不作商业评价（评述禁区见 @references/reply-style.md）+「N 项待澄清在报告里，其余按建议先行」；用户答复的澄清处理用 apply_review.py 记台账 | 已答复照办；未处理项照常进目录——涉及取值/承诺的位置只加批注，不把建议动作当结论写进正文 |
| G3 目录确认 | 第三步末 | 目录树（**评审台首建**，不带 `--pages report`） | 目录树可改 + 概要 | 划分结论（N 册及册名）+ 目录概要一行 + 三道清理一行（①②③各做了什么/跳过哪道）+「改动请在树里直接做」；拆分/装订有歧义时把选择作为明确问题问出（目录称暂定稿） | 目录按暂定稿进写作准备；用户改动落盘后增量走查回流 |
| G4/G5 指引与承诺 | 第四步（一次停轮） | 写作指引 + 承诺清单（两 tab） | 指引全量（写作构成/缺口分组）+ 承诺逐项卡（已知值直列、待补项点名）——两 tab 均只读，改动与给值走对话 | 写作构成一行（平实说法：复用历史标书/按招标格式填/据要求新写各几节——模式词不出口）+ 承诺值一行汇总（已知直列、待补点名）+「素材与值直接在对话里给我，或看完页面回『继续』」 | 未给值的落「待补」，正文相应位置只加 Word 批注点名，绝不编造；素材缺照常推理撰写/批注。答复后更新清单直接开写（开写消息带承诺值一行汇总——本门只停这一次轮） |
| G6 校验后合册 | 第六步 | 总览（待办卡）+ 写作进度面板 | 未写节在待办卡；批注清单与校验结果全量在进度面板（`check_writing --json` 落盘后刷新） | 校验结论一行 + 「批注与待办问题清单在进度页面」+ 整本 Word 文档路径 + 文档检查表（金额验算等，原样贴出，用户说修才动文件） | **校验跑完直接合册**——合册代价小（秒级重跑），用户调整都在整本层做；禁止问「现在合册还是先补齐」类岔口，补齐清单进进度页与收尾汇报由用户后续处理；对话口径见 reply-style 硬规则 9（交付物=整本 Word 文档，合册不进对话）；**招标格式件表格与原件不一致除外**（入口红线 8：先修复再合册，合册同样拒绝） |

- **标注机制（未确认 ≠ 空白）**：正文与格式件用 Word 批注（comment）点名待确认/
  待补；承诺清单值列写「待补」（全局校验自动跳过待补值，不误报）；目录说明概述
  沿用「⚠待澄清：…」标记；收尾汇报把全部未确认事项逐条点名（不可只字不提）。
- **核心纪律不变**：承诺数字只出自用户拍板的清单——批注点名待拍板事项是标注
  不是写入；「不编造」凌驾于推进效率之上。失败性停止（主文件解析失败、引擎
  校验崩溃）不属于确认门，仍按各步原文处理。
- **静态页面注意**：评审台有服务模式（GET 实时读盘，刷新即最新）与静态离线版
  （生成时点快照）两路——静态路每道门必须重跑 `build_review.py` 刷新页面再打开，
  否则用户看到的是旧数据。
- **连续模式（可选加速）**：用户明确授权「自动跑完/不用每步问我」后，G2/G3/G6
  降级为刷新页面后不停轮直接推进（页面照常刷新，默认方案与批注标注照旧；
  G1 异常门本就只在异常时停）；
  G4/G5 合并门含承诺确认，与响应文件拆分歧义一样永不降级。未授权不走此档。
- **写节前置自检（进入第五步前）**：`work/review/评审台.html` 必须已存在
  （G3 已首建停轮）、承诺卡已呈现过（G4/G5 合并门已停轮交付）、首开标记
  `work/review/.progress-opened`
  已落盘——标记=写作进度面板已首开，动作固定为第五步第一件事：
  `python3 tender-review/scripts/build_review.py --work work --open-progress`，
  把回显的面板链接发给用户；未首开时 docx_toolkit 与 check_writing --section
  会硬拦 body 节写入。三者缺任一 = 门被跳或监视面缺位，回到对应门补
  「建/刷新确认面 → 发指针 → 停轮」，补齐前禁止 create 任何节 docx（1.7.3
  真机教训：「继续」被模型读成连跑授权，四道门同轮连过、评审台在四节写完后
  才首建——本条与红线 7 是该故障的防线；2.0.0 与 2.0.4 两次真机事故同一结论：
  面板规则停在措辞层拦不住，闸必须挂在写节必经通道上，红线与路由表同步点名）。

## 台账（work/decisions.json）

记录**用户**的确认与澄清处理（对话答复；门的 pass 由 agent 写入）：
`{"gates": [{"gate": "G3", "verdict": "pass", "note": "", "at": "..."}],
"clarifications": {"CLAR-01": {"verdict": "...", "note": "...", "at": "..."}}}`。
向用户提及时说「你的确认记录」；agent 按默认方案的推进决定不写台账。
